# 0070-state-concurrency — report

## Summary (STE)

This track examined how the Zustand and xstate layer must compose to prevent races in concurrent MQTT and REST traffic. No library sells the hard parts: no monotonic-guard or ingress-dispatch middleware exists, and the one community store-machine bridge is dormant and version-pinned. We recommend a build: an owned pattern kit on the incumbent xstate 5 and Zustand 5, plus adopted test tooling. The kit contains the composition idiom, a single-dispatch ingress with monotonic guards, the cancellation standard, and an optimistic-update wrapper. We adopt fast-check for interleaving tests and the xstate/graph module in core xstate for machine-path tests. TanStack Query stays outside the transport boundary, exactly as track 0060 decided.

The most important risk is contractual: we assume the messages carry no server-issued sequence field today. Without that field, the client cannot decide stale-vs-fresh, and the interim rule is invalidate-don't-set. We raise the sequence-stamp field as a formal contract requirement to tracks 0010 and 0060. A second risk is the xstate v6 alpha, which deletes the v5 helper API. We therefore bless chart shapes and actor topologies, not helper idioms. The next step is a spike that proves the ingress seam is schedulable and runs one generated path suite.

**As of**: 2026-08-14 (versions evaluated are listed per candidate)
**Recommendation**: build (patterns) + adopt (test tooling) — build the owned Zustand-xstate composition idiom, single-dispatch ingress kit with monotonic guards, AbortSignal cancellation standard, and optimistic-update unit on the incumbents xstate 5.32.5 + zustand 5.0.15 (zero new runtime dependencies); adopt fast-check 4.9.0 with `fc.scheduler` (plus @fast-check/worker 0.6.0) as the interleaving-test lane and `xstate/graph` in core xstate ≥5.20.0 as the model-based-testing lane (never the deprecated @xstate/test); TanStack Query 5.101.4 stays in its 0060 seat outside the boundary; @xstate/store 4.2.3 is the named challenger, not adopted; RxJS 7.8.2 and Effect 3.22.1 remain prior art only per 0060

### build: the race-guard and composition pattern kit (prior-art survey)

The build candidate is the composite pattern kit — monotonic guards, version stamps, pending-write masks, write barriers, single-dispatch ingress, store-machine wiring — assembled from the documented designs of shipping real-time systems. The headline structural finding of the prior-art survey: **no surveyed shipping design decides stale-vs-fresh by wall-clock time or arrival order — every one uses an explicit server-issued authority token or dissolves the race structurally.** The tokens: Discord Gateway's per-connection sequence `s`, which clients must cache and echo in heartbeats and Resume ([Gateway docs](https://docs.discord.com/developers/events/gateway)); Linear's global `lastSyncId`, "the version number of the database", with deltas applied in sync-id order ([reverse-engineering writeup](https://raw.githubusercontent.com/wzhudev/reverse-linear-sync-engine/main/README.md)); Slack's per-channel `ts`, "guaranteed unique within the context of a channel" — an ID, not a timestamp ([docs](https://docs.slack.dev/messaging/retrieving-messages)); HTTP `ETag`/`If-Match` optimistic concurrency, preventing the lost-update problem via `412` ([MDN/RFC 9110](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/If-Match)); Replicache's per-client `mutationID`/`lastMutationID` high-water mark with rewind-and-replay rebase ([design doc](https://doc.replicache.dev/concepts/how-it-works)). The structural dissolvers: Meteor DDP's `updated` write barrier — "no particular required ordering between `result` and `updated`" messages, so the client must hold "my write is visible" until the barrier ([DDP spec](https://raw.githubusercontent.com/meteor/meteor/devel/packages/ddp/DDP.md)); TkDodo's invalidate-don't-set rule — push marks queries stale, REST remains the single writer ([Using WebSockets with React Query](https://tkdodo.eu/blog/using-web-sockets-with-react-query)); Figma's pending-write mask — "discard incoming changes from the server that conflict with unacknowledged property changes" — and its reconnect posture: download a fresh copy, reapply offline edits, continue ([multiplayer post](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)); RTK Query's streaming-updates lifecycle, which forces an ordering by awaiting `cacheDataLoaded` before attaching the socket listener ([docs](https://redux-toolkit.js.org/rtk-query/usage/streaming-updates)).

Equally load-bearing is what the survey did **not** find: no off-the-shelf monotonic-guard or ingress-dispatch middleware exists for Zustand or xstate in any surveyed ecosystem — Discord, Linear, Figma, and Replicache all built this glue bespoke at their ingress, and the gap scan confirmed no credible browser library ships it. Four independent designs converge on serialized single-dispatch ingress (Flux's singleton dispatcher with single-round updates — [archived docs](https://facebookarchive.github.io/flux/docs/in-depth-overview/); DDP's one ordered stream plus barrier; RTK Query's one-listener-one-`updateCachedData` lifecycle; Zustand's own vanilla API making one ingress module the only transport `setState` call site). The kit is therefore necessarily owned code — small (a guard is an O(1) compare plus a per-key map, tens of lines total) and confined to the choke point behind 0060's boundary. License screen on the prior art: mqtt.js is MIT despite GitHub's NOASSERTION detection ([LICENSE.md](https://raw.githubusercontent.com/mqttjs/MQTT.js/main/LICENSE.md)); **Replicache fails D-0003 as an artifact** — the shipped npm package 15.3.0 is licensed under the proprietary Replicache Terms of Service ([shipped LICENSE](https://unpkg.com/replicache@15.3.0/LICENSE), [terms](https://rocicorp.dev/terms.html)) even though the source now lives in the Apache-2.0 [rocicorp/mono](https://api.github.com/repos/rocicorp/mono) monorepo, and its successor Zero requires a self-hosted `zero-cache` server (D-0011) — design docs are citable prior art only; the wzhudev Linear writeup has [no LICENSE file](https://api.github.com/repos/wzhudev/reverse-linear-sync-engine) (all rights reserved — never vendor code from it); Flux is [archived 2023-03-21](https://api.github.com/repos/facebookarchive/flux); the [IETF Idempotency-Key draft](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/) is expired at rev 07, not an RFC — cite [Stripe's documented behavior](https://docs.stripe.com/api/idempotent_requests) instead. **Selected — the recommendation's core.**

### xstate v5 actors (5.32.5) — the architectural race-prevention substrate

MIT ([LICENSE in repo](https://raw.githubusercontent.com/statelyai/xstate/main/LICENSE)); the healthiest signal profile in the candidate list — repo pushed on the access date, three v5 patches in July 2026 (5.32.3–5.32.5) alongside the v6 alpha stream, multiple distinct human committers, [5.18M weekly downloads](https://api.npmjs.org/downloads/point/last-week/xstate), 14.5 kB gz for the whole zero-dependency actor runtime ([bundlephobia](https://bundlephobia.com/api/size?package=xstate@5.32.5)).

The race-relevant mechanics are first-party documented, not conventions. Single-writer is structural: an actor's state "can only be updated by the actor itself" and actors "process one message at a time" via their mailbox ([actor model docs](https://stately.ai/docs/actor-model)) — two async sources mutating shared state reduce to two events arriving in some order at one reducer that can arbitrate. Guards are pure `{context, event}` predicates ([guards docs](https://stately.ai/docs/guards)) — the slot a monotonic ingress guard plugs into. Invoked actors "are created and started when the state is entered, and stopped when the state is exited", and if the state exits before a promise resolves "the result of the promise is discarded" ([invoke docs](https://stately.ai/docs/invoke)) — the stale-response race dies because the receiver is gone; since xstate 5.13.0 `fromPromise` also receives an `AbortSignal` aborted on actor stop ([promise actors docs](https://stately.ai/docs/promise-actors), [core CHANGELOG PR #4832](https://raw.githubusercontent.com/statelyai/xstate/main/packages/core/CHANGELOG.md)), so it is true cancellation, not just discard. `reenter: true` restarts invoked actors — the switchMap idiom as a chart property; an event with no enabled transition in the current state causes no state change ([transitions docs](https://stately.ai/docs/transitions)) — the double-submit fix by construction. Actor systems give supervision vocabulary: `systemId` registration with root-only stop ([system docs](https://stately.ai/docs/system)) and a free [inspection API](https://stately.ai/docs/inspector).

Two findings shape the recommendation. First, the **negative finding**: neither project publishes a first-party composition pattern — Stately's [React integration docs](https://stately.ai/docs/xstate-react) never mention Zustand or any external store, Zustand's docs catalog exactly one bridge, and that bridge (zustand-middleware-xstate 3.0.1) is dormant since 2024-07-19 and pinned `zustand ^4.1.4` against a current zustand 5.0.15 ([npm](https://registry.npmjs.org/zustand-middleware-xstate)) — so the composition idiom is authored and owned by this track (Key question 2). Second, the **v6 risk**: xstate 6.0.0-alpha shipped 36 alphas in ~8 weeks (alpha.36 on 2026-08-12), and the alpha.1 notes delete the exact v5 helper surface — `setup()` "no longer registers implementations", `assign`/`raise`/`sendTo` and the `and`/`or`/`not` guard creators are removed ([alpha.1 release](https://api.github.com/repos/statelyai/xstate/releases/tags/xstate@6.0.0-alpha.1), [roadmap discussion #5061](https://github.com/statelyai/xstate/discussions/5061)). What survives intact is everything the architecture rests on: the actor model, mailboxes, invoke/spawn lifecycles, guard semantics, state-scoped cancellation. Mitigation: bless chart shapes and actor topologies, not helper-API idioms. **Selected — the process-state and orchestration layer of the built composition.**

### Zustand middleware patterns (5.0.15) — the committed-state substrate

MIT ([LICENSE](https://raw.githubusercontent.com/pmndrs/zustand/main/LICENSE)); maintenance excellent — v5.0.15 released 2026-08-13 (the day before access) on a 4–8-week all-patch cadence, 58.6k stars, [50.6M weekly downloads](https://api.npmjs.org/downloads/point/last-week/zustand), issue tracker triaged to 2 open items, tempered only by a dai-shi-centric bus factor under the pmndrs org ([contributors](https://api.github.com/repos/pmndrs/zustand/contributors?per_page=10)). Core measures 856 B min / 491 B gz ([bundlephobia](https://bundlephobia.com/api/size?package=zustand@5.0.15)).

The source-verified execution model is the substrate the race taxonomy stands on: [`vanilla.ts`](https://raw.githubusercontent.com/pmndrs/zustand/main/src/vanilla.ts) `setState` is fully synchronous — compute, `Object.assign` merge, synchronous in-order listener notification, no queueing or locking — so within one JS turn writes are atomic and ordered; across an `await` Zustand guarantees nothing ("Just call `set` when you're ready, zustand doesn't care if your actions are async or not" — [README](https://raw.githubusercontent.com/pmndrs/zustand/main/README.md)). Single-writer-per-store is documented as convention, not enforcement ([flux-inspired practice guide](https://raw.githubusercontent.com/pmndrs/zustand/main/docs/learn/guides/flux-inspired-practice.md)); any importer can call `useStore.setState(...)`, so the discipline is a lint-and-layering pattern (Key question 2). The load-bearing primitives for the built idiom: [`subscribeWithSelector`](https://raw.githubusercontent.com/pmndrs/zustand/main/src/middleware/subscribeWithSelector.ts)'s source-verified overload hands the listener `(selectedState, previousSelectedState)` — the exact shape of both a monotonic guard and a store-to-machine wire; `createStore` from `zustand/vanilla` gives non-React stores for machine-owned slices; transient `subscribe` keeps high-rate MQTT telemetry out of React renders ([README](https://raw.githubusercontent.com/pmndrs/zustand/main/README.md)); the [slices pattern](https://raw.githubusercontent.com/pmndrs/zustand/main/docs/learn/guides/slices-pattern.md) modularizes per-topic-family state with middleware applied only on the combined store. Notably, Zustand's own persist middleware reached for version-stamping to invalidate stale async work — an internal `hydrationVersion` discards in-flight rehydration reads ([PR #3555](https://github.com/pmndrs/zustand/pull/3555), [v5.0.10](https://github.com/pmndrs/zustand/releases/tag/v5.0.10)) — first-party prior art for exactly this track's stale-vs-fresh guard. **Selected — the committed-domain-data and UI-state layer of the built composition.**

### @xstate/store (4.2.3) — named challenger, not adopted

MIT (same repo [LICENSE](https://raw.githubusercontent.com/statelyai/xstate/main/LICENSE)); 4.2.3 released 2026-08-10 ([npm](https://registry.npmjs.org/@xstate/store/latest)), 3.4 kB gz, zero dependencies ([bundlephobia](https://bundlephobia.com/api/size?package=@xstate/store@4.2.3)); React bindings split into [@xstate/store-react 2.0.0](https://registry.npmjs.org/@xstate/store-react/latest) (peer react ^18||^19, built on `useSyncExternalStore`). By the vendor's own positioning it is a direct Zustand-category competitor ("similar to Redux or Zustand, but with less boilerplate" — [Stately blog](https://stately.ai/blog/2024-04-10-xstate-store)), and it genuinely embodies this track's discipline: writes only through named events (`store.trigger.*` — a structural single dispatch path), `store.can` guards, an inspectable event log via `.inspect()`, and `fromStore()` promoting a store to actor logic ([docs](https://stately.ai/docs/xstate-store)); TkDodo's third-party endorsement corroborates the API quality ([Introducing XState Store](https://tkdodo.eu/blog/introducing-x-state-store)).

Not adopted, on three grounds. (1) **Maturity gap**: [~144.7k weekly downloads](https://api.npmjs.org/downloads/point/last-week/@xstate/store) — ~0.3% of Zustand's 50.6M — and four major versions in ~26 months; [v4.0.0 (2026-05-27)](https://github.com/statelyai/xstate/releases/tag/%40xstate%2Fstore%404.0.0) was breaking (bindings split, `createStoreWithProducer` removed, undo/redo reshaped) — a real annual migration tax against stores that would otherwise be stable Zustand code. (2) **Redundancy**: the properties it sells — event-driven single write path, guards, inspection — are exactly what the blessed composition already obtains from the incumbent pair (machines and `fromTransition` actors for concurrency-exposed state; Zustand modules exporting only actions); adopting it would put a third state technology in the app for benefits the composition already has. (3) **Bus factor and v6 coupling**: [package commits](https://api.github.com/repos/statelyai/xstate/commits?path=packages/xstate-store&per_page=15) are overwhelmingly one maintainer's, and store v4 pairs with xstate v5 while core v6 is in alpha — `fromStore()` compatibility across that transition is unverified. Disposition: **named challenger**. Reopen if the hand-rolled single-writer discipline proves unenforceable — migration is vendor-documented as cheap in both directions and `createStoreHook` mimics Zustand's hook shape, so the option stays open at low cost.

### TanStack Query (@tanstack/react-query 5.101.4) — adopted in its 0060 seat; race ledger audited

MIT ([LICENSE](https://raw.githubusercontent.com/TanStack/query/main/LICENSE)); the healthiest candidate in the set — releases days apart, [63.7M weekly downloads](https://api.npmjs.org/downloads/point/last-week/@tanstack/react-query), multi-maintainer TanStack org, no react-query v6 on npm (the [solid-query 6.0.0-rc.0](https://api.github.com/repos/TanStack/query/releases?per_page=10) signals an eventual cycle), 17.0 kB gz including query-core ([bundlejs](https://deno.bundlejs.com/?q=@tanstack/react-query@5.101.4); ~14.0 kB gz per [bundlephobia](https://bundlephobia.com/api/size?package=@tanstack/react-query@5.101.4), a narrower single-package measurement). 0060 adopted it **outside** the boundary; this track's contribution is the audited race ledger (Key question 5), source-verified in query-core.

**Free**: per-key request dedup — an in-flight fetch's promise is returned to concurrent callers, verified in [query.ts](https://raw.githubusercontent.com/TanStack/query/main/packages/query-core/src/query.ts); per-key response ordering — dedup plus `cancelRefetch: true` default cancels the old fetch before a new one ([QueryClient reference](https://tanstack.com/query/latest/docs/reference/QueryClient)), so a stale REST response can never overwrite a newer one within a key, inside the cache; staleness bookkeeping with refetch on mount/focus/reconnect ([important defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults)); mutation serialization via `scope.id` and offline mutation ordering ([mutations guide](https://tanstack.com/query/latest/docs/framework/react/guides/mutations)). **Not provided**: mutation dedup — "all mutations run in parallel - even if you invoke `.mutate()` of the same mutation multiple times" (same guide) — double-submit is not solved. **Recipes, races if unwritten**: cancellation is inert unless the queryFn consumes the provided `AbortSignal` ([query cancellation guide](https://tanstack.com/query/latest/docs/framework/react/guides/query-cancellation)); the optimistic-rollback idiom is `cancelQueries` + snapshot + rollback ([optimistic updates guide](https://tanstack.com/query/latest/docs/framework/react/guides/optimistic-updates)), and the concurrent-mutation residual race is maintainer-documented with the `isMutating() === 1` invalidation gate as the fix ([TkDodo, Concurrent Optimistic Updates](https://tkdodo.eu/blog/concurrent-optimistic-updates-in-react-query)). **Remains for this track**: everything MQTT-shaped, plus the finding that even inside the cache, an in-flight REST fetch resolving after a push-driven `setQueryData` overwrites the fresher pushed data — Query is last-write-wins with no version guard. The full seam and the entity-ownership adjudication are under Key question 5. **Selected — adopt, outside the boundary, seam unchanged.**

### fast-check (4.9.0) — adopted: the interleaving-test lane

MIT ([LICENSE](https://raw.githubusercontent.com/dubzzz/fast-check/main/LICENSE)); 4.9.0 released 2026-07-08 on a ~4–8-week cadence, repo pushed 2026-08-12, [30.4M weekly downloads](https://api.npmjs.org/downloads/point/last-week/fast-check), npm OIDC trusted publishing; TS ≥5.0, ES2020, one runtime dependency, zero production footprint. Bus factor ~1 ([dubzzz 2,793 commits vs 14 for the next human](https://api.github.com/repos/dubzzz/fast-check/contributors?per_page=10)) — held at strong maintenance rather than demoted because of 9 years of history, no architectural churn in flight, and the low strand-cost of a test-time dependency.

`fc.scheduler()` is a stable, first-class race-detection arbitrary whose `act` hook exists "to be able to test React components against race conditions" ([3.9.0 release post](https://fast-check.dev/blog/2023/05/21/whats-new-in-fast-check-3-9-0/)); the repo ships six race examples, including a React + RTL property (~30–35 lines) asserting a page never renders stale data for a superseded ID ([userProfile example](https://raw.githubusercontent.com/dubzzz/fast-check/main/examples/005-race/userProfile/main.spec.tsx)) — structurally identical to this app's headline race. Three findings shape adoption. (1) **The seam constraint is architectural**: the [docs' own limitation list](https://fast-check.dev/docs/advanced/race-conditions/) states uncontrolled sources — external fetch and event emitters — cannot be managed, so mqtt.js itself cannot be scheduled; race properties must inject scheduled synthetic messages and scheduled REST resolutions at the single validated-dispatch seam of Key question 7. Race properties become cheap only after the ingress seam exists — build order matters. (2) **Pattern pioneering**: authenticated GitHub code search finds zero indexed pairings of `fc.scheduler` with Zustand or xstate; the closest published analog is [dotvvm's ~70-line store stress test](https://raw.githubusercontent.com/riganti/dotvvm/main/src/Framework/Framework/Resources/Scripts/tests/stateManagement.stress.test.ts). The team writes largely without community templates. (3) **CI mechanics are clean**: failures print `{seed, path, endOnFailure}` for deterministic replay ([test reports docs](https://fast-check.dev/docs/tutorials/quick-start/read-test-reports/)); `fc.schedulerFor([ordering])` pins a discovered interleaving as a permanent regression test — the artifact every fixed race bug should leave behind; [@fast-check/worker 0.6.0](https://registry.npmjs.org/@fast-check/worker/latest) (MIT, same monorepo [LICENSE](https://raw.githubusercontent.com/dubzzz/fast-check/main/LICENSE), accessed 2026-08-14) kills hung properties without taking the runner down; `numRuns` is globally configurable for per-PR vs nightly budgets. First-party runner adapters exist ([@fast-check/vitest 0.4.1](https://registry.npmjs.org/@fast-check/vitest/latest), peer `vitest ^4.1.0`; [@fast-check/jest 2.2.0](https://registry.npmjs.org/@fast-check/jest/latest)); raw `fc.assert` works in any runner regardless. **Selected — adopt.**

### @xstate/test (0.5.1) — eliminated as-named; capability adopted as `xstate/graph` in core xstate (≥5.20.0)

The plan's listed candidate is dead as-named: npm marks [@xstate/test](https://registry.npmjs.org/@xstate/test) **deprecated** ("Please use @xstate/graph instead."), latest stable 0.5.1 from 2022-01-27 with peer `xstate ^4.29.0` — uninstallable against v5; its 1.0.0-beta line stalled 2024-01-11 and never went stable. Installing it would pin the app to xstate v4. The plan's verification note ("historically lagged xstate major versions") resolved better than expected: the capability moved **into core xstate** at 5.20.0 (2025-06-19, [PR #5287](https://github.com/statelyai/xstate/pull/5287)) under the `xstate/graph` subpath — `createTestModel`, `getShortestPaths` (Dijkstra), `getSimplePaths`, `getPathsFromEvents`, `getAdjacencyMap`, path dedup, plus 5.30.0's guard-aware `filterEvents` traversal option ([core CHANGELOG](https://github.com/statelyai/xstate/blob/main/packages/core/CHANGELOG.md)); the [official testing docs](https://stately.ai/docs/testing) confirm the move. The version-lag problem is structurally gone — the test utilities now version with core, the graph module is present on the v6-alpha main branch, and adoption costs **zero new packages**.

Integration is a framework-agnostic forEach — `model.getShortestPaths().forEach(path => it(path.description, () => path.test(...)))` — and event executors are arbitrary async functions, so generated paths can drive the boundary mocks and assert taxonomy/quarantine states directly, no adapter layer needed. Flags: no v4-style `testCoverage()` report (coverage discipline is "run all generated paths" plus dedup); thin official docs — [discussion #5286](https://github.com/statelyai/xstate/discussions/5286) records the gap; and a design decision to bless — maintainer guidance in [discussion #4761](https://github.com/statelyai/xstate/discussions/4761) prefers abstract models of the system under test over reusing production machines. The superseded standalone [@xstate/graph 3.0.4](https://registry.npmjs.org/@xstate/graph) (2025-05-31, peer `xstate ^5.19.4`, directory removed from the monorepo) is the same trap, milder: stopgap only if the app is stuck below 5.19.4. **Capability selected — adopt as `xstate/graph`; the report and all CI docs must use that name.**

### RxJS (7.8.2) — prior art only, per binding 0060 decision

Apache-2.0 ([LICENSE.txt](https://raw.githubusercontent.com/ReactiveX/rxjs/master/LICENSE.txt)). Surveyed strictly as prior art — 0060 rejected adoption, and this track's own findings independently reinforce it: the stable line has gone ~18 months without a new release (7.8.2, published 2025-02-22 — [npm registry](https://registry.npmjs.org/rxjs)), v8 was abandoned in alpha, and the [9.0.0-beta.0 release](https://github.com/ReactiveX/rxjs/releases) (2026-08-04) self-describes single-maintainer publishing. Decisively, **RxJS 9 retires the very machinery adoption would have bought**: cancellation moves from Subscription teardown to platform `subscribe(cb, {signal})` semantics on the WICG Observable ([v9 README](https://raw.githubusercontent.com/ReactiveX/rxjs/master/packages/rxjs/README.md), [WICG proposal](https://github.com/WICG/observable)). What the prior art contributes (Key question 6): the three flattening idioms' exact semantics from shipped [7.8.2 JSDoc](https://raw.githubusercontent.com/ReactiveX/rxjs/7.8.2/src/internal/operators/switchMap.ts) — switchMap (take-latest, cancel previous), exhaustMap (drop-while-busy), concatMap (queue, with its own [unbounded-buffer warning](https://raw.githubusercontent.com/ReactiveX/rxjs/7.8.2/src/internal/operators/concatMap.ts)) — and three hardening rules from [`fromFetch`](https://raw.githubusercontent.com/ReactiveX/rxjs/7.8.2/src/internal/observable/dom/fetch.ts): internal controller aborted by teardown, external signal chained in (hand-rolled `AbortSignal.any()`), and the `abortable` commit-point flag — cancellation must no-op after the result is handed over. All three translate to plain xstate/Zustand at zero dependency cost.

### Effect (3.22.1) — prior art only, per binding 0060 decision

MIT ([LICENSE](https://raw.githubusercontent.com/Effect-TS/effect/main/LICENSE)); very healthy (pushed on the access date, ~296 contributors, corporate steward) and mid 3-to-4 major transition (4.0.0-rc.109 published on the access date) — an adoption-timing flag that is moot in the assigned prior-art role. What the prior art contributes (Key question 6): the best-specified interruption model surveyed — child fiber lifetime bounded by parent, `Fiber.interrupt` waits for finalizers, cascading interruption, race interrupts the loser ([Fibers](https://effect.website/docs/concurrency/fibers/), [Basic Concurrency](https://effect.website/docs/concurrency/basic-concurrency/)) — and the decisive bridge design, source-verified at the [3.22.1 tag](https://raw.githubusercontent.com/Effect-TS/effect/effect%403.22.1/packages/effect/src/Effect.ts): every promise-wrapping constructor receives an `AbortSignal` aborted on fiber interruption, with the honest gotcha that "the underlying asynchronous operation only stops if it observes that signal". This is verbatim the contract xstate ≥5.13.0 exposes in `fromPromise` — Effect's interruption model is already present in the incumbent, which is why the translation costs nothing.

### Wave 2 gap scan — challenger and residual finds

A category sweep (Zustand middlewares, xstate ecosystem, async-coordination, optimistic-update helpers, testing tools, race-lint rules) surfaced one challenger and a dozen absorbable finds; every find was dispositioned. No SSPL or source-available candidate surfaced anywhere in the scan (D-0003/D-0011 clean).

- **`xstate/graph` in core (CHALLENGER)** — absorbed as a candidate and **adopted**; replaces @xstate/test as the model-based-testing vehicle (its own Survey subsection above).

## Key questions

**1. Race taxonomy: which races does this app face, and what evidence exists for each?**
All five race classes named in the plan are real for this traffic shape, each attested in shipping systems' own documentation. (1) **Stale REST response vs fresher MQTT event** — the generic form is in React's own docs (racing effects, the `ignore`-flag cleanup — [Synchronizing with Effects](https://react.dev/learn/synchronizing-with-effects)); the REST-vs-push specialization has three documented treatments: RTK Query's lifecycle forces an ordering (await `cacheDataLoaded` before attaching the socket listener), TkDodo's invalidate-don't-set makes REST the single writer, and Meteor DDP's `updated` write barrier handles "my POST returned but the push echo has not arrived". Additionally, even inside a TanStack-managed cache, an in-flight REST fetch resolving after a push-driven `setQueryData` overwrites the fresher pushed data — Query is last-write-wins with no version guard. (2) **Out-of-order MQTT messages** — the [MQTT 5.0 spec](https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html) guarantees ordering only per topic within a flow on one connection (section 4.6); nothing across topics, and re-sent PUBLISH packets are duplicates with DUP set (section 4.4); [Ably's docs](https://ably.com/docs/connect/states) prove ordering cannot be delegated to the pipe even under managed resume. The canonical client fixes are server-issued sequence tokens (Discord `s`, Linear `lastSyncId`, Slack `ts`). (3) **Double-submit** — TanStack Query does **not** solve it (mutations run in parallel by default); the documented fixes are xstate finite states client-side (an event with no enabled transition causes no state change) plus Stripe-style idempotency keys server-side (the IETF draft is expired; backend support is an unfilled fact). (4) **Optimistic-update rollback** — TanStack's own docs codify snapshot/rollback with the mandatory `cancelQueries` first step; the concurrent-mutation residual race is maintainer-documented, with the `isMutating() === 1` gate as the fix; Figma's pending-write mask and Replicache's rebase (rollback is re-execution, not undo) are the rigorous prior art. (5) **Reconnect replay** — duplicates (QoS 1 redelivery with DUP; retained messages re-arrive on every re-subscribe; mqtt.js defaults `resubscribe: true` and `queueQoSZero: true` replay the client's own buffered publishes) and gaps (under the assumed `clean: true` there is no broker-side gap fill — every reconnect is a Figma-style "assume you missed things" moment, answered by invalidate/refetch). Evidence caveat (D-0004): the app's actual bug history is an unfilled fact — this taxonomy is derived from the traffic shape in the plan and documented prior art, not observed incidents (A-12).

**2. Which races are solved architecturally, and what are the blessed Zustand-xstate composition patterns?**
Architecturally solved, by chart/store shape with no tooling needed: **stale REST response** — invoked-actor discard plus real cancellation (state exit stops the actor, the `fromPromise` signal aborts the fetch); **concurrent-writer races** — single-writer actors (mailbox linearizes) and single-writer stores (Zustand's synchronous commit makes same-turn writes atomic; across an `await` the single-writer rule is a lint-and-layering convention, not an enforcement); **out-of-order and stale-vs-fresh** — monotonic guards at the owning reducer (xstate guard `event.seq > context.lastAppliedSeq`, or the `(next, prev)` compare in a store action) — xstate supplies the guard slot, not the metadata (Key question 7); **double-submit** — finite states: in `submitting` the second SUBMIT has no enabled transition and is dropped by construction; **optimistic rollback** — explicit `optimistic → confirmed | rolledBack` states rather than ad-hoc store patches, with the Key question 5 unit where Query is in play; **reconnect replay** — the 0060-owned connection machine exposes reconnect; the rule here is treat reconnect as a gap, invalidate/refetch push-covered entities, and make reducers idempotent against QoS-1/retained duplicates.

The blessed composition patterns — the core owned deliverable, since neither project publishes one and the only community bridge is dormant and version-pinned: (1) **State placement**: xstate machines own *process* state — anything with a lifecycle (in-flight requests, submissions, connection presentation, per-feature orchestration); Zustand stores own *committed domain data* and UI/preference state; TanStack Query's cache owns REST server-state above the boundary. No entity's authoritative copy lives in two of these at once (adjudication in Key question 5). (2) **Machine-to-store wire**: `actor.subscribe(snapshot => store.setState(project(snapshot)))` — the machine remains the single writer of its projected slice; components may instead read actor state directly via `@xstate/react` `useSelector` (rerenders only when the selected value changes). This wire carries continuous state — connection presentation and full snapshots; discrete domain events (contract-break emissions, one-shot business events) instead cross through the boundary's typed `actor.on`/`emit()` emitted-event surface, per 0060 Key question 1 — the two wires are complementary, not competing. (3) **Store-to-machine wire**: `subscribeWithSelector`'s source-verified overload hands the listener `(selectedState, previousSelectedState)` — diff the slice, `actor.send()` on meaningful transitions; the `(next, prev)` pair is also the exact shape of a hand-rolled monotonic guard. (4) **Non-React stores**: `createStore` from `zustand/vanilla` for machine-owned child stores; transient `subscribe` (no re-render) for high-rate MQTT telemetry into refs/canvases. (5) **Single-writer enforcement**: each store module exports only action functions; the raw hook/`setState` stays unexported; oxlint `no-restricted-imports` bans `mqtt`, the raw generated client, and store internals outside owning modules — the same three-layer coverage mechanism 0010 adopted (D-0002). (6) **v6-proofing**: xstate 6.0.0-alpha deletes the exact v5 helper surface (`setup()` registration, `assign`, named guards, `and`/`or`/`not`) while keeping the actor model, mailboxes, invoke/spawn lifecycles, and guard semantics intact — **bless chart shapes and actor topologies, not helper-API idioms**, and colocate machine definitions for a mechanical migration.

**3. Which races are solved by tooling, and what is the CI shape?**
Tooling catches what architecture cannot make structurally impossible: interleaving bugs inside the blessed patterns, and regressions of the patterns themselves. Two adopted lanes, deliberately non-overlapping: **`fc.scheduler` owns interleavings** and **`xstate/graph` owns machine-path coverage** (fast-check's own `fc.commands` model-based mode is not used for machine paths, to avoid duplicating lanes). The fast-check lane carries an architectural precondition: the scheduler cannot manage uncontrolled event emitters, so mqtt.js cannot be wrapped — race properties inject scheduled synthetic messages and scheduled REST resolutions at the Key question 7 dispatch seam, which means **race properties become cheap only after the ingress seam exists**. The `xstate/graph` lane costs zero new packages and one forEach per model; paths drive the boundary mocks and assert taxonomy/quarantine states directly. **Lint — the honest gap**: under the incumbent oxlint (D-0002), the one ESLint rule that specifically detects await-interleaved assignment races, `require-atomic-updates`, is absent from oxlint's 849-rule list. What lint genuinely contributes: layering enforcement via `no-restricted-imports` (the single-writer and single-ingress disciplines are lintable) plus type-aware `no-floating-promises`/`no-misused-promises`. The oxlint JS-plugins alpha opens a future path to a small custom race-rules plugin; eslint-plugin-xstate is pre-flat-config and unusable on that path without a fork. **Stated explicitly: await-interleaving races are covered by architecture and tests, not lint, in this stack today.** CI shape: per-PR — layering lint, the race-property suite at reduced `numRuns` (~50), and all generated `xstate/graph` paths (shortest-paths, dedup, and `filterEvents` keep counts tractable); nightly — higher `numRuns` (~250) under `@fast-check/worker`; every fixed race lands an `fc.schedulerFor` regression property.

**4. @xstate/store: does it replace or complement Zustand in this stack?**
Complement in principle; **not adopted now**. It is a direct Zustand-category competitor by the vendor's own positioning and genuinely embodies this track's discipline (named-event writes as a structural single dispatch path, `store.can` guards, inspectable event log, `fromStore()` promotion to actor logic). But the survey weighs against adoption today: the maturity gap (~0.3% of Zustand's adoption; four majors in ~26 months — an annual migration tax), redundancy with the chosen architecture (the properties it sells are exactly what Key question 2's patterns already obtain from the incumbent pair — adopting it would put a third state technology in the app for benefits the composition already has), and bus-factor/v6 coupling (near-single-author package; `fromStore()` compatibility across the core v6 transition unverified). Disposition: **named challenger, not adopted** — reopen if the hand-rolled single-writer discipline proves unenforceable in practice; migration is documented as cheap in both directions, so the option stays open at low cost.

**5. TanStack Query overlap with 0060: which races disappear for free, and which remain?**
The ownership boundary, restated verbatim from 0060's report (binding):

> **TanStack Query lives OUTSIDE (above) the transport boundary. The boundary exports validated, branded, taxonomy-erroring request functions — 0010's mutator-wrapped orval client — and those functions are the queryFns. TanStack Query owns, above the boundary: caching, request deduplication, retries (via a taxonomy-aware predicate that retries only class-1 transport errors), background refetch, offline pause/resume, and cancellation signaling. The boundary owns, below the queryFn seam: validation, reason-code parsing, taxonomy mapping, branding, and quarantine. Nothing inside the boundary imports or depends on TanStack Query.**

Nothing in this track contradicts that seam, and the four-class error taxonomy remains owned by `transport-boundary/errors` (0060 Key question 3) — this report cites it and relocates nothing. **Free** (source-verified in query-core): per-key request dedup; per-key response ordering (dedup plus default `cancelRefetch` — a stale REST response can never overwrite a newer one within a key, inside the cache); staleness bookkeeping with refetch on mount/focus/reconnect (`refetchOnReconnect` gives free REST-side reconnect recovery); mutation serialization via `scope.id`; offline mutation ordering. **Recipes, races if unwritten**: cancellation (inert unless the queryFn consumes the signal — the 0060 spike item verifies orval threads `signal` through the mutator) and optimistic rollback (`cancelQueries` + snapshot + rollback + the maintainer-documented `isMutating() === 1` gate must ship as one non-optional wrapper, a shared `useOptimisticMutation` — a prime `fc.scheduler` target). **Remains for this track**: stale-REST-vs-fresher-MQTT arbitration (Query has no knowledge of the MQTT leg and is last-write-wins even against push-driven `setQueryData`); out-of-order MQTT; MQTT reconnect replay; double-submit (no mutation dedup exists — the fix is Key question 2's `submitting` state, with `scope.id` as wire-level backstop); cross-key consistency; and the entity-ownership question 0060 left open (its risk 6), which this track now adjudicates. **Adjudication — partition entity ownership; invalidate-don't-set as the interim bridge.** REST-backed entities live in the QueryCache and are read via query hooks; MQTT-only entities live in Zustand/machine state behind the Key question 7 ingress guard. For entities served by both legs, under the assumed absence of ordering stamps (A-1), the blessed rule is TkDodo's invalidate-don't-set: the MQTT event carries identity, not authority — it invalidates the matching query (`staleTime: Infinity` on push-covered queries) and REST remains the single writer of the cache; the stale-vs-fresh comparison never happens rather than being decided. If and when the contracts gain server-issued version stamps (the Key question 7 contract request), both legs pass through the same per-(topic, entity) monotonic guard, and push may then write `setQueryData` directly (preceded by `cancelQueries`) where round-trip cost matters. Copying query data into Zustand is banned — it reintroduces one layer down every race Query just solved.

**6. Cancellation idiom: which does the app standardize on, and how does it cross the 0060 boundary?**
**Standardize on `AbortController`/`AbortSignal` propagation, with xstate invoke-per-state as the take-latest mechanism.** The ecosystem has converged on `AbortSignal` from three independent directions: RxJS 9 retires its own Subscription-teardown cancellation for platform `subscribe(cb, {signal})` semantics; Effect bridges fiber interruption to an `AbortSignal` handed to every promise constructor (source-verified at 3.22.1); and xstate ≥5.13.0 passes an `AbortSignal` into `fromPromise` that aborts on actor stop. The app therefore gets switchMap-class semantics with zero new dependencies — reinforcing 0060's non-adoption of RxJS and Effect, which this track assesses strictly as prior art per the binding constraint. The translated idiom set: **switchMap** (take-latest) — a state invoking `fromPromise(({input, signal}) => fetch(url, {signal}))`, retriggered with `reenter: true`: actor stop, signal abort, network cancel; the Zustand-only fallback is a store-held `AbortController` plus a monotonic epoch, where the epoch check before `set()` is what actually prevents the stale write. **exhaustMap** (drop-while-busy) — free: no enabled transition for the trigger event in the busy state. **concatMap** (queue) — **do not translate**: its own JSDoc warns the buffer is unbounded, and for state ingress a monotonic stale-drop guard beats ordering-by-queueing. **Structured-concurrency rule** (from Effect): spawn async work as child actors of the machine that owns the result — never free-floating promises — so cancellation is scope exit, not bookkeeping. **Hardening rules** (from RxJS `fromFetch` and Effect): every app-written async function takes and forwards an `AbortSignal`; define the commit point after which cancellation must no-op rather than corrupt (check `signal.aborted` before committing); compose a boundary-owned signal with per-actor signals via `AbortSignal.any()` ([Baseline 2024](https://developer.mozilla.org/en-US/docs/Web/API/AbortSignal/any_static)) so logout or connection loss aborts everything in flight. **Crossing the 0060 boundary**: two signal owners, one primitive, one seam. For query-driven fetches, TanStack Query owns the signal and the boundary threads it through the orval mutator into `fetch` — the 0060 spike's decisive check. For machine-driven fetches, the `fromPromise` signal passes through the **same** mutator. An aborted request rejects with `AbortError` before validation and is treated as a cancellation outcome, not classified into the four-class taxonomy — a normalization detail to record with the owners of `transport-boundary/errors` (0060's module; this track cites it and adds no classes). On the MQTT leg, per-request cancellation does not apply — delivery is subscription-scoped — so staleness there is handled by Key question 7's ingress guards, not cancellation.

**7. Ingress ordering: how does validated 0060 output enter stores, and what guard decides stale-vs-fresh?**
**Exactly one validated dispatch path per topic, owned as code just behind the 0060 boundary's egress.** Four independent designs converge on serialized single-dispatch ingress (Flux's dispatcher, DDP's ordered stream plus barrier, RTK Query's one-listener lifecycle, and Zustand's vanilla API making a single ingress module the only transport `setState` call site). Notably absent everywhere: an off-the-shelf monotonic-guard middleware — every shipping system builds this glue bespoke. The pipeline, in order, per validated message emitted by 0060's actor surface: (1) **idempotence/dedup**, keyed on packet identity (messageId + topic under A-8), because QoS 1 duplicates and retained-message re-arrivals are protocol-legal; (2) **per-(topic, entity) monotonic guard** where the contracts carry a server-issued sequence/version stamp — compare stamps, highest wins, regressions dropped declaratively (xstate guard or the `(next, prev)` compare in a store action); MQTT's per-topic-per-connection ordering scope makes *(topic, entity id)* the natural key; (3) **invalidate-don't-set fallback** where no stamp exists — the event triggers an authoritative refetch instead of writing payload data (the interim default under A-1); (4) **pending-write mask** — entities with in-flight optimistic mutations shadow incoming server data until acknowledged (Figma's rule; TanStack's `cancelQueries` + `isMutating` is the cache-side equivalent); (5) **dispatch** — one store action per topic family (the only writer of that slice) or `actor.send` to the owning machine. **The stale-vs-fresh decision**: REST responses for push-covered entities pass through the **same guard, keyed the same way** — that single shared guard is what makes "stale REST response vs fresher MQTT event" decidable rather than racy. The decisive dependency is contractual, not tooling: **stamp-based adjudication requires a server-issued monotonic field modeled in the vendored AsyncAPI payload schemas (and ideally the matching REST bodies) so it survives 0010's validation boundary.** This track raises that as a formal contract requirement to 0010/0060. Until it lands, invalidate-don't-set is the blessed default, reconnect is treated as a gap (invalidate/refetch push-covered entities), and the guard code ships stamp-ready. This dispatch path is also the schedulable seam Key question 3's fast-check properties require — one build, two payoffs.

Eliminated early or scoped out of the table: **@xstate/test** as-named (npm-deprecated, stable 0.5.1 from 2022 with peer `xstate ^4.29.0` — installing it would pin the app to xstate v4; capability adopted as `xstate/graph` in core); **zustand-middleware-xstate 3.0.1** (dormant since 2024-07-19, zustand-v4-pinned, replaces ~30 lines of stable-API glue — prior art only); **zustand-xs 0.0.1** (never-iterated proof-of-concept); **eslint-plugin-xstate 3.2.1** (pre-flat-config, cannot ride oxlint's ESLint-v9 JS-plugin path without a fork — rule catalog retained as prior art); **Replicache** (the shipped npm artifact is under proprietary Terms of Service — **fails D-0003**; its successor Zero needs a self-hosted server — D-0011; design docs remain citable prior art); **wzhudev/reverse-linear-sync-engine** (no LICENSE file — documentation only, never vendor); **facebookarchive/flux** (archived — concept only) and the **IETF Idempotency-Key draft** (expired — cite Stripe instead); **leo-query** (~667 weekly downloads, stalled RC — dominated by the adopted TanStack Query); **zundo** (history-revert is the wrong shape for concurrent rollback); **SWR** (adds nothing over TanStack Query); **TanStack Pacer** (beta — the named watch item); **Effection** (occupies the slot 0060 closed); **xstate-audition** (spike-deferred, ~388 weekly downloads); **async-mutex/p-queue** (locks are the wrong primary shape; p-queue named as the blessed residual primitive); **use-optimistic-reducer / floppy-disk / zustand-mutative** (dormant / negligible adoption / out of scope). Ably, Linear, Figma, Discord, and Slack are proprietary systems — documentation-grade prior art only, never candidates.

## Recommendation

**Shape: build (the composition patterns and race-guard kit) + adopt (the test tooling)** — of the four shapes, this is a **build**, exactly the "build (patterns) + adopt (test tools)" outcome the plan's verification notes anticipated. It composes with, and nowhere reopens, 0060's build of the `transport-boundary` package.

**What is built** (owned patterns, each with named shipping prior art):

1. The **Zustand-xstate composition idiom** (Key question 2): the state-placement rule (machines own process state; stores own committed domain and UI state; the QueryCache owns REST server-state), the two wiring directions on stable first-party primitives for continuous state (`actor.subscribe` → `store.setState`; `subscribeWithSelector` `(next, prev)` → `actor.send`) — discrete domain events cross instead via 0060's typed `actor.on` emitted-event surface (0060 Key question 1) — vanilla stores for machine-owned slices, transient subscriptions for high-rate telemetry — blessed as **chart shapes and topologies, not v5 helper idioms** (v6-proofing).
2. The **single-dispatch ingress kit** (Key question 7): one validated dispatch path per topic behind 0060's actor surface — dedup, then the per-(topic, entity) monotonic guard where stamps exist (else invalidate-don't-set), then the pending-write mask, then a single store action or `actor.send`; reconnect treated as a gap. Tens of lines, O(1) per message, doubling as the schedulable seam for the race-property suite.
3. The **cancellation standard** (Key question 6): `AbortSignal` propagation end to end — invoke-per-state as switchMap, machine event-dropping as exhaustMap, epoch/commit-point guards for bare-Zustand async, `AbortSignal.any()` composition with the boundary signal, no concatMap translation.
4. The **optimistic-update unit** (Key question 5): a shared wrapper bundling `cancelQueries` + snapshot/rollback + the `isMutating` invalidation gate as one non-optional piece, plus the enforced single-writer/layering lint rules (oxlint `no-restricted-imports`, D-0002).

**What is adopted**: **fast-check 4.9.0** with `fc.scheduler()` as the interleaving-test lane (plus **@fast-check/worker 0.6.0** for hang protection; @fast-check/vitest or @fast-check/jest once the framework fact resolves); **`xstate/graph` in core xstate ≥5.20.0** as the model-based-testing lane (zero new packages; the deliverable must never name @xstate/test); **TanStack Query 5.101.4** in exactly its 0060 seat — outside the boundary, seam restated verbatim under Key question 5 — with this track's adjudication of the entity-ownership question 0060 left open (partition, with invalidate-don't-set as the interim bridge). **p-queue 9.3.3** is named as the blessed residual coordination primitive for the rare genuine queue/limit need outside the actor system.

**What is explicitly not adopted**: @xstate/store 4.2.3 (named challenger — complement in principle, redundant with the composition today, ~annual major churn); RxJS 7.8.2 and Effect 3.22.1 (prior art only, per binding 0060 — their idioms are extracted at zero dependency cost); @xstate/test / zustand-middleware-xstate / zustand-xs / eslint-plugin-xstate / leo-query / zundo / SWR / TanStack Pacer (beta watch item) / Effection / xstate-audition (spike-deferred) / async-mutex (acknowledged fallback only); Replicache fails D-0003 as an artifact and is prior art only.

**Rationale.** The evidence is unanimous that the hard part of this track is not purchasable: no off-the-shelf monotonic-guard, ingress-dispatch, or store-machine composition library exists in any surveyed ecosystem — every shipping system that solved these races (Discord, Linear, Figma, Replicache, Meteor) built the same small glue at its ingress, and the only published Zustand-xstate bridge is dormant and version-pinned. The incumbents already contain the architectural mechanisms (single-writer actors with mailboxes, guard slots, invoke-lifecycle cancellation with `AbortSignal`, a synchronous single-commit store with `(next, prev)` subscriptions), so the marginal dependency cost of the architecture is zero. Where tooling genuinely helps — schedule-fuzzing interleavings and generating machine-path tests — best-in-class OSS exists and is adopted; where the plan assumed tooling exists (race lint), the honest finding is that it does not under oxlint today, and this report says so. The single most consequential external dependency is contractual, not a library: server-issued ordering stamps in the vendored schemas, raised as a formal requirement to 0010/0060.

**Constraints applied**: D-0001 (desk research only; every open verification lands in the spike section), D-0002 (coverage and layering lint stays on oxlint `no-restricted-imports`; no new lint toolchain; the race-lint gap is stated rather than papered over), D-0003/D-0011 (every recommended piece is MIT or Apache-2.0 OSS with in-repo license files verified; Replicache's shipped artifact is flagged as failing D-0003 and its successor Zero as colliding with D-0011; proprietary systems are prior art only), D-0004 (facts/app-profile.md is unfilled; every substituted assumption is declared below), D-0006 (validated messages enter state only through the boundary — the ingress kit sits behind 0060's choke point and extends its coverage into the state layer), D-0007 (STE summary above), D-0010 (0010's artifacts consumed as delivered — orval mutator client, compiled Ajv validators, four-class taxonomy, reject-and-quarantine; nothing here reopens 0010).

**Risks:**

1. **xstate v6 rewrites the v5 helper surface** (36 alphas in ~8 weeks; `setup()` registration, `assign`, named guards all deleted). Mitigation: bless chart shapes/topologies, isolate helper-API touchpoints, colocate machine definitions. The actor model, mailboxes, lifecycles, and guard semantics — everything the architecture actually rests on — survive v6.
2. **Ordering metadata is assumed absent** (A-1, the pivotal unknown): until the contract request lands, stamp-based adjudication is impossible and the app pays invalidate-don't-set's extra round-trips; if the contracts can never carry stamps, stale-vs-fresh remains structurally undecidable at the client and invalidate-don't-set becomes permanent.
3. **Pattern pioneering**: zero public `fc.scheduler` + Zustand/xstate prior art exists — the team writes the first published flavor of these race properties, and the pattern kit is owned code forever (mitigated by its small size and the copied designs).
4. **Sequencing constraint**: race properties are only writable after the single-dispatch seam exists (the scheduler cannot wrap event emitters) — the ingress kit must land before the test suite pays off; build order matters.
5. **Lint cannot catch await-interleaving races** in this stack today (no `require-atomic-updates` in oxlint; the JS-plugins path is alpha) — coverage rests on architecture plus tests; a custom plugin is a future hardening option, not a plan dependency.
6. **Discipline-dependent adjudication**: the QueryCache/Zustand partition and the single-writer rules are conventions enforced by layering lint, not by any library; the lint rules are definition-of-done, not polish (0060's risk 6 closes only if they land).
7. **fast-check bus factor ~1** (2,793 commits vs 14 for the next human) — mitigated by 9 years of history, massive adoption, and the low strand-cost of a test-time dependency.
8. **TanStack Query hazards inherited from 0060** remain live obligations above the seam: the taxonomy-aware retry predicate (defaults silently retry class-2 violations), signal threading through the orval mutator (silent no-op if dropped), and no mutation dedup (double-submit is the machine's job).

**Assumptions declared in place of facts (D-0004; facts/app-profile.md is unfilled — each is a question for the app owner):**

- **A-1 (pivotal)**: MQTT payloads carry **no** server-issued sequence/version field today; invalidate-don't-set is the interim rule and the stamp is a raised contract requirement. If the field is present, the monotonic guard applies directly.
- **A-2**: React ≥18 (zustand v5 / @xstate/react / react-query peer floors), with React 19 unknown — `useOptimistic` positioning is conditional on 19.
- **A-3**: TypeScript ≥5.4 (TanStack Query's stated support window; xstate needs ≥5.0, fast-check ≥5.0).
- **A-4**: The app's xstate is v5 and can move within-v5 to **≥5.20.0** (for `xstate/graph`; ≥5.13.0 is the floor for the `fromPromise` signal). A v4 app would invalidate the zero-marginal-cost argument and require migration first.
- **A-5**: Zustand is v4 or v5 with an acceptable path to 5.x; usage is idiomatic hook-style stores without exotic middleware.
- **A-6**: mqtt.js 5.x over WSS at documented defaults (`clean: true`, `resubscribe: true`, `queueQoSZero: true`), QoS 0/1, a **single** client connection (multiple connections would void the per-topic ordering baseline).
- **A-7**: Peak MQTT rate ≤ ~1k msg/s (0010's assumption carried forward) — makes synchronous listener fan-out and per-message guard cost immaterial.
- **A-8**: No ordering metadata means dedup keys on packet identity (messageId + topic).
- **A-9**: Test framework is jest or vitest (vitest assumed; the adapters' peer ranges need checking, and raw `fc.assert` removes the dependency on this fact).
- **A-10**: No team veto exists against RxJS/Effect; 0060 rejected both on rubric/evidence grounds (bundle cost, redundancy with incumbents, mid-transition maintenance risk), not on measured team sentiment. Team statechart and property-testing experience is assumed none (the conservative integration-cost read).
- **A-11**: oxlint is recent enough for the JS-plugins alpha if a custom rule is ever pursued (consistent with 0010's assumption); the layering rules need only `no-restricted-imports`, which is present.
- **A-12**: No store-level race bug history is available — the taxonomy and idiom priority follow the traffic shape, not incidents; the "which stores and machines exist today" inventory is likewise unfilled.
- **A-13**: Backend idempotency-key support is unknown — client-side double-submit protection stands alone until answered.
- **A-14**: Browser targets are evergreen/Baseline-2024 (`AbortSignal.any()` availability); older targets need manual listener chaining.

## What a spike would validate

Pre-scoped per D-0001; each item is a go/no-go check. The first four extend 0060's spike list; the rest are this track's own.

- **Composition wiring end to end**: implement one machine → vanilla store → React path for continuous state (`actor.subscribe` → `setState` → `useSelector`) and one store → machine path (`subscribeWithSelector` `(next, prev)` → `actor.send`) on the app's actual xstate/zustand versions — discrete-event wiring via 0060's `actor.on` surface is validated in 0060's own spike (0060 Key question 1); measure the glue in lines and confirm no feedback loop or re-entrancy hazard under synchronous listener fan-out.
- **Schedulable ingress seam (decisive for the test lane)**: prototype the single-dispatch ingress function (dedup → guard → mask → dispatch) and write one `fc.scheduler` property against it with scheduled synthetic MQTT messages racing a scheduled REST resolution; confirm the stale write is rejected and the failure replays from `{seed, path}`. Fail: the seam design must change before the kit is finalized.
- **Regression pinning**: convert the property's found interleaving into an `fc.schedulerFor` test and confirm it runs deterministically in CI; wire `@fast-check/worker` and confirm a deliberately hung property is killed without taking the runner down.
- **`xstate/graph` path suite**: generate and run one shortest-paths suite (with `filterEvents`) against a small production-shaped machine on the app's actual xstate minor; confirm ≥5.20.0 is reachable as a semver-minor upgrade; decide abstract-model vs production-machine reuse; assess whether xstate-audition's helpers are worth vendoring for live-actor assertions.
- **Cancellation chain**: verify actor stop aborts a real fetch through the orval mutator (`fromPromise` signal → mutator → `fetch`), that `AbortError` is normalized as a cancellation outcome (not a taxonomy class) with the `transport-boundary/errors` owners, and that `AbortSignal.any()` composition with a boundary-owned signal aborts all in-flight work on simulated connection loss.
- **Optimistic-update unit**: implement the shared `useOptimisticMutation` wrapper (`cancelQueries` + snapshot + rollback + `isMutating` gate) and subject it to an `fc.scheduler` property interleaving two mutations and a refetch — the maintainer-documented residual race is the acceptance test.
- **Invalidate-don't-set bridge**: wire one push-covered query (`staleTime: Infinity`, MQTT event → `invalidateQueries`) and confirm no path copies query data into Zustand; verify the layering lint (oxlint `no-restricted-imports`) rejects a deliberate violation of the single-writer and no-store-copy rules in this repo's oxlint version.
- **Contract question (raise now, not in the spike)**: put the server-issued ordering-stamp requirement to the app owner and 0010 — per-entity version or per-topic sequence in the vendored AsyncAPI payload schemas and matching REST bodies; the guard code ships stamp-ready either way.
- **Fact re-checks that could flip calls**: the app's actual xstate and zustand majors (A-4/A-5), React 19 (A-2, `useOptimistic`), the test framework (A-9, adapter peer ranges), and the real peak MQTT rate (A-7).
