**Status**: open
**Owner**: app owner

Track 0100-type-strictness (D-0021) rests on a premise no app-profile field records: the
codebase receives a high volume of agent-authored code, and enforcement must survive
that. An adversarial review of the track's research plan found this premise had no
intake route, so declaring it as an assumption would leave the assumption doing all the
work. The pseudo-monorepo layout fact adds a second cluster: the TypeScript
configuration shape, which three separate investigations each had to assume
differently. Resolving: fill in facts/app-profile.md (some items need a new section) and
flip this Status to resolved.

## a — how agent-authored code lands

What is the volume and shape of agent contributions — rough PR count or size per week,
and how large is a typical agent-authored change? Who reviews them, and is review
per-PR or sampled? Do agents run the typecheck and linters locally before pushing, or
does CI find the failures first? This decides the single biggest design choice in the
track: **diff-scoped gates** (changed files must be strict; cheap to satisfy per PR,
strong against high volume) versus **global-metric gates** (a percentage that can be
raised by polishing files nobody was worried about). It also shapes what the per-PR
output must look like for a human to review it at speed.

→ Resolution: the answer → adds a "How code lands" section to facts/app-profile.md and
selects the 0100 gate shape

## b — may an agent fix its own failing gate?

When a type or lint gate fails on an agent-authored PR, does the failure route back to
the agent to fix, or to a human? This is the question that decides whether suppression
gates work at all: if an agent may resolve its own gate failure, then every suppression
mechanism the track recommends is also a suppression *generator*, and the design must
shift to mechanisms an agent cannot satisfy by suppressing (diff-scoped strictness with
no suppression path, or human-owned config).

→ Resolution: the answer → adds to the "How code lands" section and constrains which
0100 mechanisms are viable

## c — who owns the enforcement configuration?

Every mechanism this track will recommend is a committed file in the same repo the
agents write to: `tsconfig.json` strictness flags and include/exclude globs, lint
configs, any strictness allowlist, stored ratchet thresholds, committed baselines (0030
already has one; 0020's ratchet lives in inline `biome-ignore` comments), and — specific
to this layout — the **single root `package.json` `scripts` block**, where one edit can
blunt every gate at once because there are no per-package scripts to edit instead.

Add to that list the **alias tables**: tsconfig `paths`, plus whatever restates them for
the bundler and the test runner. These do not look like enforcement files, but any
boundary rule keyed to an `@appname/...` specifier is defeated by adding one new mapping
that points a second alias at the same directory — an edit that reads as routine wiring
and will not draw enforcement-grade review.

Are any of these files protected today (CODEOWNERS, required human review, branch
protection)? This program already has a confirmed precedent for the failure mode: D-0020
exists because an oxlint `overrides` entry silently dropped a base ban list.

→ Resolution: the answer → adds to the "How code lands" section and decides whether
0100 must recommend config-ownership controls alongside the gates themselves

## d — TypeScript configuration shape and alias mechanism

How many `tsconfig.json` files exist and where — one at the root, or one per
pseudo-package directory (and do any use `extends` or project `references`)?

The alias *mechanism* is now known (facts/app-profile.md, 2026-08-14): internal imports
are written `@appname/path/to/thing`, so a `paths` mapping certainly exists. The
remaining question is narrow and load-bearing: **does the tsconfig also carry
`baseUrl`?** Before TypeScript 4.1 a `paths` mapping *required* `baseUrl`, so repos of
this vintage usually still carry it even though `paths` no longer needs it.
**TypeScript 7.0 removed `baseUrl`** and the oxlint type-aware lane reports it as a hard
error, so if it is present, migrating it away (fold the prefix into each `paths` entry,
which resolves relative to the tsconfig file) is a prerequisite for the fast lint lane
regardless of every other decision in this track.

Also needed: **where else is the `@appname` alias configured** — the bundler's resolver,
the test runner, any lint import resolver? Each place that restates the mapping rather
than deriving it from tsconfig is a drift risk, and the `baseUrl` migration may need to
touch each of them in step. The same tsconfig drives dependency-cruiser's alias
resolution in the 0090 wiring, so these migrations must be sequenced together rather
than owned separately.

→ Resolution: the answer → adds a TypeScript configuration line to
facts/app-profile.md, unblocks the 0100 lane routing, and sequences the alias migration
with the 0090 dependency-cruiser wiring

## e — is per-directory strictness wanted, and is directory ownership a goal?

Should different pseudo-package directories be allowed to sit at different strictness
levels (a legacy directory permitted to lag while new directories are held strict), or
is one repo-wide standard preferred? Relatedly: is it a goal to enforce that a given
directory may not import another directory's code or dependencies? Nothing enforces
either today — with one dependency list, knip structurally cannot attribute a dependency
to a directory, and per-directory strictness needs either project references or a
hand-maintained invocation list, both of which are real work worth doing only if wanted.

→ Resolution: the answer → decides whether 0100 recommends per-directory ratcheting or
a single repo-wide gate, and whether directory-boundary rules join the 0090
dependency-cruiser adoption
