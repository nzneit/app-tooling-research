# 2026-08-14: 9900 process-design scope rulings (intake)

**Status**: open
**Owner**: user (repo owner — these are rulings about this repo, not app facts)

Track 9900-process-design (D-0025) needs two rulings before its survey can produce a
recommendation rather than a menu. Both are decisions only the repo owner can make: one
is a constraint boundary that gates an entire class of candidate, and the other sets the
budget the recommendation must fit inside. Resolving: answer here, and each allocates or
updates a `D-####`.

## a — does "dependency-free root" bar a CI-installed binary?

The spike-harness spec states the repo root `package.json` stays dependency-free and the
validator stays zero-dep, and the root manifest today declares no `dependencies` and no
`devDependencies` at all. The question the track cannot answer for itself: does that rule
constrain **npm dependencies specifically**, or **any external tool in the checking path**?

It matters because the two strongest external candidates are standalone binaries, not npm
packages: **Vale** (prose linting — the only credible route to mechanically enforcing any
part of the ASD-STE100 rule the spec claims is validator-enforceable) and **lychee**
(external link checking — the validator currently skips every `http(s)` URL, so the repo
verifies none of its own citations). Neither would appear in `package.json`. Both would be
a new thing a contributor or CI must install.

Three possible rulings: (i) **npm-only** — binaries are fine, tool candidates are live;
(ii) **strict** — nothing outside Node's standard library enters the checking path, so
every improvement must be an in-house `check-docs.ts` extension and the tool candidates are
eliminated on constraint rather than on merit; (iii) **CI-only** — binaries may run in CI
but never in the pre-commit path, keeping local work dependency-free.

→ Resolution: the ruling → allocates a `D-####` recording the dependency envelope, and
either admits or eliminates the tool half of 9900's candidate list

## b — the per-track ceremony budget

Four independent research strands seeded this track and every one proposed adding steps;
none proposed removing any. Stacked, they would add roughly five to eight mandatory
authoring and review steps per track — against a defect record of a handful of corrections
across fourteen tracks. The track is instructed to price every control and report the net
change in steps, but it needs a target to aim at.

Which is wanted: (i) **net steps must fall** — a new control must retire or merge an
existing one, forcing consolidation; (ii) **net steps hold** — additions are allowed only
where offset; (iii) **net steps may rise**, up to a stated ceiling, because correctness is
worth more than speed here. Also useful: is per-track wall-clock, human review time, or
agent token spend the cost you actually care about, since they trade against each other.

→ Resolution: the ruling → sets the constraint 9900's recommendation is scored against,
and is recorded in the acceptance decision for its report
