# 2026-08-17: 0150-message-inbox — facts the track cannot proceed without (intake)

**Status**: open
**Owner**: app owner (a–h, j–k), plus legal/procurement (l) and the contract owners (c)

Track [0150-message-inbox](../tracks/0150-message-inbox/research-plan.md) asks whether selected
inbound MQTT streams should get a durable inbox. Items **a–d** gate the survey rather than
colour it: under one set of answers the recommendation is **skip** and no storage candidate
needs comparing. Partial answers are fine, and "I don't know" is itself an answer worth
recording — several of these are observations nobody has had reason to make yet.

## a — MQTT session mode, and is the clientId stable?

Does the client connect with `clean: true` (mqtt.js's default) or `clean: false`? And is the
clientId stable across reloads and across tabs, or mqtt.js's per-instance random default?

This is the track's null hypothesis. Under a clean session the broker keeps no session state,
so there is no cross-reload QoS 1 redelivery at all — redelivery happens only within a live
connection, and that is already handled by the in-memory dedup guard accepted in D-0015 and the
ingress LRU accepted in D-0016. If `clean: true` holds and no other duplicate source exists
(see **e**, **h**), the durable half of this track has no traffic to act on. 0060 recorded
`clean: true` as **assumption A-5**, never as a confirmed fact.

→ Resolution: confirms or defeats the null hypothesis → updates facts/app-profile.md

**2026-08-17 update — ANSWERED, and the null hypothesis is defeated.** The user: the session
runs **`clean: false` with a persisted clientId**. Recorded in facts/app-profile.md. The track
is live; skip is no longer its default verdict. Four consequences, propagated: 0060's A-5 and
0070's A-6 are falsified and both accepted reports now carry dated in-place corrections; the
mqtt.js #909 duplicate history A-5 excluded is back in scope; a reconnect is no longer
automatically a gap for QoS 1 (0070's rule is now over-conservative there, safe but costly);
and `resubscribe: true` is redundant against a retained session while still re-triggering
retained delivery on every reconnect.

One consequence was not anticipated by this item and is now the plan's centre of gravity.
mqtt.js sends the PUBACK **from inside the `handleMessage` callback**, and the default handler
completes immediately — so the acknowledgement precedes any async work the app starts. A
persistent session therefore gives the *appearance* of at-least-once delivery across reloads
while a crash between acknowledgement and effect loses the message permanently and silently.
Losing a message is worse than applying one twice. Deferring the ack is the fix, and it
collides head-on with 0060 Key question 5's "never do slow work in `handleMessage`". That
collision is plan question 2.

## b — Which streams, and are their effects idempotent?

The charter says "certain arbitrary messages". Which topics or streams are those, roughly what
share of the ~50 msg/s peak do they carry, and — the question that actually decides the design
— **are their effects idempotent?**

An effect that replaces or invalidates (last-write-wins, "refetch this entity") is already
safe under redelivery and needs no inbox. An effect that accumulates — appends to a list,
increments a counter, enqueues work, fires a notification, triggers a REST write — is the only
kind that an inbox protects. If every stream is in the first category, the answer is skip.

→ Resolution: scopes the track, or ends it → updates facts/app-profile.md

## c — Is there a stable per-message identifier today, and can one be added?

Does any payload already carry a field that is unique and stable per logical event — a message
id, sequence number, or server-assigned identifier? MQTT itself supplies none: the Packet
Identifier is a per-session slot released for reuse once acknowledged, so it cannot survive a
reload, and QoS 0 has no identifier at all.

If no such field exists, the dedup key must be a hash of the canonicalized payload, which is
strictly worse (see **e**) — so the alternative is a contract change. Note this is a **sibling
of D-0019, not the same request**: D-0019 asks for a monotonic *ordering* stamp (which of two
messages is fresher), and this asks for an *identity* key (have I seen this exact message).
They answer different questions and one does not imply the other. But they go to the same
contract owners, so asking together is one conversation instead of two.

→ Resolution: selects the dedup-key branch → may extend the D-0019 contract request

## d — Where do effects land today — durable storage, or memory only?

The inbox pattern requires the identity write and the effect write to share one transaction. If
message effects are applied only to in-memory Zustand/xstate state and never persisted, **there
is nothing for the key write to be atomic with**, and the pattern collapses to a durable
seen-set — a much smaller thing that should not be called an inbox. Does the app persist any
state to IndexedDB or localStorage today? If so, under what database name and schema version,
and who owns migrations?

→ Resolution: fixes the transaction scope → updates facts/app-profile.md

## e — Retained messages and overlapping topic filters

Two MQTT behaviours produce deliveries that are byte-identical to an already-processed message
but are **not** duplicates, and a content-hash dedup key would silently swallow both:

1. **Retained messages.** [MQTT-3.3.1-6] requires the broker to send the last retained message
   on every new subscription, and mqtt.js defaults `resubscribe: true` — so every reconnect
   re-triggers it. Suppressing this is actively harmful: 0060 treats every reconnect as an
   unrecoverable gap, and the retained message is the repair.
2. **Overlapping filters.** MQTT 3.1.1 §3.3.5 permits one copy per matching subscription where
   a client's filters overlap. Those copies are intended deliveries.

Do any subscribed topics carry retained messages? Does the client subscribe to overlapping
filters (a wildcard plus a more specific filter that both match)?

→ Resolution: constrains the dedup key → updates facts/app-profile.md

## f — Multiple tabs, and the scope of the persisted clientId

**Raised in priority by the 2026-08-17 answer to item a, and the first half may be a live defect
rather than a design question.** With `clean: false` and a *persisted* clientId, the scope of
that id decides which of two failure modes the app has today:

- **Shared across tabs** (persisted in `localStorage` or similar): MQTT requires the broker to
  disconnect an existing client when a second connects with the same ClientId
  ([MQTT-3.1.4-2]). Two tabs would evict each other in a reconnect loop, each takeover
  producing a reconnect the other treats as a gap. If this is the configuration and multi-tab
  is a supported scenario, it is a defect that exists independently of any inbox work.
- **Per-tab** (persisted in `sessionStorage`, or derived per connection): every tab ever opened
  leaves an abandoned persistent session on the broker, which keeps queueing QoS 1 messages
  against subscriptions no one will ever read, until a session-expiry policy reaps it. That is
  a broker-side resource question and needs the expiry setting.

Which is it — and is there a session-expiry interval configured on the broker?

Then the original question: can one user have several tabs open against the same broker, and is
state expected to be shared or independent between them? Tabs share one IndexedDB but hold
independent MQTT connections, so the same logical message can arrive twice into one shared
store.

0060 dismissed cross-tab coordination on **assumption A-13** ("no multi-tab coordination
requirement exists") and explicitly flagged it as reopening if tabs share a connection. Durable
storage is cross-tab by construction where the current in-memory dedup is not, so this track
reopens the question regardless of A-13's fate. This overlaps the still-open multi-tab item in
the Wave 2 intake; answering it here settles both.

→ Resolution: decides whether leader election is in scope → updates facts/app-profile.md

## g — Has a duplicate ever actually been observed?

Has anyone seen a duplicate-applied effect in production — a bug report, a support ticket, a
user-visible symptom — and roughly how often? The track currently has no baseline and cannot
size its own win without one. A confident "no, never" is a strong input, not a gap.

→ Resolution: sizes the problem, or supports a skip

## h — Broker topology and protocol version

Is the broker clustered, bridged, or fronted by shared subscriptions? Each can duplicate a
message independently of QoS, which changes what the dedup key must be stable across. (Item a
already defeated the null hypothesis, so this no longer decides whether the track runs — but a
clustered or bridged broker widens what the key must be stable across, and a clustered broker
also raises whether the persistent session in item a is pinned to one node.)

Two settings now travel with this: what **session-expiry interval** is configured (how long the
broker holds an offline session's queue), and what **queue depth limit** the broker enforces
per session. At ~50 msg/s these size the reconnect replay burst that plan question 5 measures
against 0060's bounded delivery queue — which sheds *oldest* at a default of 256.

Separately: which MQTT protocol version does the client negotiate, 3.1.1 or 5.0? This decides
two things — whether MQTT 5 User Properties and Correlation Data are available as a place to
carry the identifier in **c**, and which acknowledgement-deferral seam exists at all
(`customHandleAcks` is silently a no-op below protocol version 5; `manualAcks` does not exist
in mqtt.js at any version).

→ Resolution: constrains the dedup key and the ack seam → updates facts/app-profile.md

## i — What durability is actually wanted, and can the Firefox floor move?

Must the inbox survive an **OS crash or power loss**, or is a tab crash / page reload the only
failure it needs to survive? This is not a detail. IndexedDB gives genuine all-or-nothing commit
across object stores on both target engines, but it does **not** give a flush guarantee: Firefox
has been relaxed since version 40 and exposes no `durability` option below 126 — the stated
floor is ~124 — and Chromium's default is now relaxed too. Chrome's own documentation states
that even `strict` "does not ensure that changes are actually written immediately to disk".

If reload survival is enough, the answer is comfortable. If power-loss safety is required, the
honest report cannot promise it on this matrix, and the follow-up is whether the Firefox floor
can move to 126+.

→ Resolution: fixes what the report may claim → updates facts/app-profile.md

## j — Storage budget, privacy, and the reset path

Four smaller questions that travel together:

- What retention window and storage budget is acceptable for the inbox (records, bytes, or
  days)? Browser eviction is whole-origin and LRU by default; `navigator.storage.persist()`
  exempts an origin but prompts the user in Firefox — is that prompt acceptable?
- Are there **privacy, retention, or encryption constraints** on writing contract payloads (or
  effects derived from them) to durable browser storage? This has never been tested here: 0060
  deliberately kept the quarantine ring in memory and never shipped its contents.
- Must the app work in private/incognito windows, where IndexedDB works but is destroyed at
  session end — degrading silently rather than failing visibly?
- What is the support reset path for local state today? Once the inbox is durable, "reload
  fixes it" stops being true, and clearing site data becomes the only recovery from a poisoned
  store.

→ Resolution: sets retention, quota, and recovery policy → updates facts/app-profile.md

## k — Web Workers and cross-origin isolation

Is a Web Worker or SharedWorker available and architecturally acceptable for storage work, or
must this run on the main thread alongside the existing xstate actor system? And can the
deployment set COOP/COEP cross-origin-isolation headers?

These two answers alone decide whether the SQLite-WASM-over-OPFS branch is a live option or
dead on arrival: its full VFS is Worker-only and needs cross-origin isolation. A "no" to both
narrows the survey usefully and early.

→ Resolution: prunes the candidate set → updates facts/app-profile.md

## l — Licence posture on two edge cases

Two questions the research cannot answer:

1. Is **AGPL-3.0-only** acceptable for a library bundled into the shipped browser application?
   The shared rubric flags copyleft rather than barring it, so this is a ruling, not a lookup.
   It decides whether Triplit can be considered at all.
2. Is a dependency whose licence is **declared in package metadata but evidenced by no licence
   text** in the repo or the published tarball acceptable? This is not hypothetical:
   `@sqlite.org/sqlite-wasm` ships no licence file anywhere, and `tab-election`'s only licence
   evidence is a manifest string. Does the organisation's CI run licence scanning or SBOM
   generation that would fail on these?

→ Resolution: decides eligibility for three candidates → may allocate a D-#### if it sets a
general rule

## m — Is a real-browser test lane reachable?

The track's central claim is "a crash between applied and recorded cannot double-apply". The
standard test tool, `fake-indexeddb`, is an in-memory reimplementation of exactly the
auto-commit and durability timing under test — it can confirm the design's shape and never its
guarantee. Both prior spikes reached only Node and happy-dom, never a browser.

Is there an existing e2e/browser harness (or would track 0120 provide one) that could host real
IndexedDB atomicity assertions? If not, the report will say plainly that its central claim is
unverified, which is an acceptable outcome but should be a known one.

→ Resolution: sets the verification bar → may bound what the track can conclude
