### D-0019: Server-issued ordering stamp — contract requirement with graceful fallback
**Date**: 2026-08-14
**What**: The program formally requests a server-issued monotonic ordering stamp (per-entity version or per-topic sequence) in the vendored contracts — raised to the app owner and 0010 via intake item a. Measured basis (0070 spike): without a stamp the client cannot even observe a lost REST-vs-MQTT race (`stats.stale === 0`, final version 1 of 3); with one, the same guard rejects the stale write in every interleaving fc explores and the invalidate round trip disappears (tests: ingress-race both arms, replay-and-pinning, bridge stamped-fast-path). The requirement is deliberately flexible: adoption is per-stream opt-in (one `stamp` selector plus an optional `write`, no interface reshaping); any existing monotonic field present on both legs may serve as the stamp — no new field is needed where one already exists; contracts we do not control stay partitioned or on invalidate-don't-set indefinitely, which remains the sanctioned safe bridge (D-0016).
**Why**: Stale-vs-fresh arbitration is provably undecidable client-side without a stamp, and per-stream opt-in means partial contract control cannot block incremental adoption.
**From**: tracks/0070-state-concurrency/spikes/ingress-and-test-lane/findings.md (user call at the Wave 3 gate)
**Affects**: 0010, 0060, 0070, contract owners

### D-0023: Track 0100 adds a tenth rubric criterion — Suppression auditability
**Date**: 2026-08-14
**What**: Track 0100-type-strictness scores its candidates against the shared nine-criterion rubric **plus one track-specific tenth criterion, "Suppression auditability"**, weighted high. It scores how visible and reviewable a mechanism's suppressions are: an *auditable* escape is inventoried, budgeted, and countable (a sidecar suppressions file, a shrinking allowlist, an unused-suppression report); a *silent* escape is a comment that turns the rule off with no inventory. ### D-0024: Split the TypeScript 7 question — migration in 0100, compiler upgrade later
**Date**: 2026-08-14
**What**: The TypeScript 7 question splits in two. **Track 0100 owns the bounded part**: removing `baseUrl` (removed in TS 7.0, and rejected as a hard error by oxlint's type-aware lane) and migrating the `@appname/*` alias to `paths`-only form, which is a no-op for the alias mapping itself but requires auditing bare imports that relied on `baseUrl`'s fallback-root role — those can silently retarget to a same-named real package rather than failing. The sanctioned detection step is to pass through TypeScript 6.0 without `"ignoreDeprecations": "6.0"`, which surfaces every fallback-dependent import as a deprecation error. **A separate, not-yet-minted track owns the rest**: upgrading the app's own `typescript` dependency from 5.9.3 to 7.x. Adopting the fast type-aware lint lane does **not** require the upgrade, because `oxlint-tsgolint` bundles its own typescript-go engine.
**Why**: The two halves have different costs, different blockers, and different owners. Folding a compiler-major migration into a strictness track would make 0100 unable to produce one coherent recommendation, while leaving the `baseUrl` work out of 0100 would block its own lane routing.
**From**: 0090/0100 verification workflows (user call 2026-08-14)

### D-0027: Dependency envelope — a four-rung ladder, strict by default
**Date**: 2026-08-14
**What**: The "dependency-free root" rule is a **preference ladder, not a prohibition**. Each rung requires justification to climb, and the default is the lowest. **Rung 0 — strict** (default): the improvement is an in-house `check-docs.ts` extension using only Node's standard library; nothing new enters the checking path. **Rung 1 — npm-only**: an npm dependency is permitted for things that do not make sense to roll ourselves. **Rung 2 — CI-only**: an external binary may run in CI but not in the pre-commit path, when we truly cannot live without the tooling. **Rung 3 — forced local install**: a binary every contributor must install, permitted only where there is no practical way to replicate the tool's fidelity in-house *and* the CI expense of rung 2 would be too great. Rungs 2 and 3 are not ordered by contributor burden — rung 3 asks more of contributors than rung 2 — but by where the cost lands; the choice between them is a cost-placement decision, not an escalation of permissiveness. Vale is the named example that may reach rung 2 or 3, because mechanical ASD-STE100 checking has no clear in-house equivalent at comparable fidelity. This supersedes nothing: it interprets the spike-harness spec's "the repo root `package.json` stays dependency-free and the validator stays zero-dep" (D-0017), which constrained npm dependencies and was silent on binaries.
**Why**: User ruling 2026-08-14 on intake item a, which the 9900 track could not decide for itself because it is a constraint boundary rather than a tool comparison. ### D-0029: The ceiling's unit — a "step" is a logical workflow step
**Date**: 2026-08-17
**What**: Under the **net steps hold** ceiling (intake 2026-08-14 item b), a **step** means *a logical step in the workflow, or dynamic workflow, that executes a track* — an orchestration stage such as investigate, verify, critique, price, or synthesise. It does **not** mean a line of prose, a validator check, or a document someone may read. Consequences: a rung-0 validator check is ceiling-free; a byte added to an always-loaded file is ceiling-free; a new named pass in the execution of a track is ceiling-**governed** and needs an offset. Two things follow that the report did not assume. First, the ceiling now governs **how tracks are run**, not only what authors must do — so the shape of the agent workflow that executes a track is the budgeted object. Second, because always-loaded bytes are ceiling-free but recur on every session of every track forever, they must still be **priced and reported** in the agent-token unit; ceiling-free is not cost-free, and a report that omits that price is incomplete.
**Why**: User ruling 2026-08-17 on intake item a. The 9900 report assumed a step was "a mandatory per-track authoring or review action" (its assumption A-1) and flagged that its arithmetic was contingent on the definition. The actual intent was neither that reading nor the broader "anything an author or agent must do or read". The report's four shipped items stay free under this reading, so its recommendation is unaffected; what changes is that future proposals are scored against workflow stages rather than authoring actions. **This supersedes assumption A-1 of the 9900 report**, which is annotated in place there.

**Affects**: every future control proposal; the 9900 report's step arithmetic; the design of track-executing workflows

### D-0030: Payment classes — a cancelled proposal is not an offset
**Date**: 2026-08-17
**What**: Under net steps hold, an offset must retire, merge, or time-box something **that exists**. A **cancelled proposal** — paying by not building something that was never built — is **not** admitted as payment. The two adjacent classes the survey also invoked are constrained with it: a **future rate-limit** (a promise to constrain later additions) is not payment because it retires nothing now, and a **tooling offset** (retiring a candidate never adopted) is not payment for the same reason. An offset names a thing currently in the process and removes it.
**Why**: User ruling 2026-08-17 on intake item b, confirming the 9900 report's recommendation. The class is unfalsifiable: any control can name a hypothetical it forecloses, so admitting it makes the ceiling unenforceable in principle rather than merely lenient. Nine of the survey's 43 proposed controls paid in one of these three classes, and three separate controls each claimed to be the budget authority for the others — which cannot all be true, and is the symptom this rules out.

### D-0039: Run a 0150 spike ahead of the survey; size for full retention, design for none
**Date**: 2026-08-18
**What**: Track 0150-message-inbox runs a **spike before its survey and before its report**, on user directive. That guarantee is client-owned, holds at any QoS under any broker, and survives the Mosquitto migration below untouched, which is why it is the half worth building today. **Guarantee B** — offline retention and redelivery — is broker configuration and is exercised only where a Node-hosted broker can reach it. The spike must record plainly which of its checks the available lanes cannot run, per plan question 16: an in-memory reimplementation of IndexedDB cannot test durability across a real crash by construction, and neither prior spike in this repo reached a real browser.
**Also ruled here — the retention assumption, and how to size against it.** Roughly 75% of the ~34 non-inbox topics are subscribed at QoS 1, which on a `clean: false` session makes ActiveMQ create a durable subscription for each whether or not the app wanted one. Asked which of them genuinely need offline retention, the user answered honestly that it is not known offhand, expects **none** of them do, and offered to plan for the worst and assume **all** do. The ruling splits the two: **size for all, design for none, and record the gap as a measurable quantity rather than an assumption.** Sizing for all is the safe direction and costs nothing but arithmetic — it is what makes ~32 durable subscriptions per device, ~39 msg/s of durable traffic, ~3,200 outstanding prefetch, and ~140,000 messages per offline hour the planning figures rather than the 6-topic numbers they replace. Designing for all is the unsafe direction: it would build machinery for a case the person closest to the app expects does not exist, and it forecloses the demotion audit that is the single cheapest available remedy. **The reframing that makes the question answerable**: "does this topic need offline retention?" is a judgement call nobody can make from memory, but it reduces to "**is this topic's effect accumulating or replacing?**" — and that is answerable by reading the handler. A replacing effect (last-write-wins state, "refetch this entity") needs no offline retention, because the next message after reconnect supplies the current value; only an accumulating effect (append, increment, enqueue, notify, trigger a write) does. That is the same test intake item b already applies to the 6 inbox candidates, now extended to the other ~26, and it turns a vibes-level estimate into a code-reading task the app team can complete. The report must not treat the user's "probably none" as a fact — it is a hypothesis with a named test.
**Also recorded — the Mosquitto migration has a horizon: 3 to 6 months** (user, 2026-08-18). That is inside the service life of anything designed now, so plan question 19's premise is **settled affirmative**: the report designs for both brokers rather than treating portability as hypothetical. The practical consequence is that ActiveMQ-specific behaviour may not appear as a design assumption anywhere in the deliverable — it belongs in a compatibility matrix beside Mosquitto's, with a per-broker minimum-configuration checklist. The two brokers fail in opposite directions and neither default is adequate: ActiveMQ durable subscriptions never drop and accumulate against disk with a full store blocking every publisher, while Mosquitto defaults to `max_queued_messages` 1000 per client dropping **newest**, which at this app's ~39 msg/s of QoS-1 traffic is roughly **26 seconds** of offline retention, or about three minutes after a successful demotion audit. Covering a single overnight absence on Mosquitto needs a value near 144,000, two orders of magnitude above default, and it is invisible from the client. The migration also **re-inverts a correction this program already made**: `resubscribe: true` was recorded as redundant, corrected to required once ActiveMQ turned out not to restore QoS-0 subscriptions, and becomes redundant again on Mosquitto, which restores them per §3.1.2.4. ### D-0042: Intake form convention — two item shapes, options with a recommendation, clause-by-clause answer checking
**Date**: 2026-08-23
**What**: `intake/_TEMPLATE.md` gains a required shape, and answering an intake file gains a required check. **Item shape, by kind.** A **fact item** (a size, a version, a rate, what already exists) offers no options — it carries instead the assumption the work will proceed on if the item goes unanswered, with that assumption's consequence if wrong, so the cost of skipping the item is visible at the moment of skipping (this is D-0004's declared-assumption rule moved upstream of the report). A **ruling item** (a choice) carries what is true today with a citation, numbered options, a recommendation that argues why each alternative loses, and an enumeration of what inherits the answer — tracks, reports, decisions, and any accepted text that would need marking superseded. **One item = one answerable question**; an item with parts numbers its parts. **Acceptable non-answers are pre-declared** in the item ("I don't know", "nobody has measured"), because an unstated one comes back blank instead. **Answer intake** is the half that was missing: when answers arrive, each item's question is re-read clause by clause against its answer; every unanswered clause stays open and is named in the file's header note; an answer *outside* the offered options is a first-class outcome that is specified before it is recorded; and an answer the owner delegates to the agent is recorded as delegated, naming the evidence it was decided on. The header note lists what resolved, what was allocated, what came back **partial**, and what is still open. No existing intake file is rewritten (D-0009: resolved files stay in place). No track workflow gains a stage, so the D-0029 ceiling is untouched; the always-loaded price is one bullet in `CLAUDE.md` growing by ~55 words, reported here per D-0029's standing rule.
**Why**: User directive 2026-08-23, and the 0160 round is the evidence. Twelve items came back answered; **six settled less than their question asked**, and four of those were initially read as closed — a described scrubbing *mechanism* read as a ruled disclosure *policy*, an *available* device identifier read as a *permitted* one, a *defined* build-id format read as a *runtime-readable* one, and an endpoint's size answer read as covering compression. All four were caught by a verification pass over the revision rather than by the form, which is the wrong place to catch them. ### D-0043: Memory budgets are per track — each track states and bounds its own
**Date**: 2026-08-23
**What**: Every track that holds memory on the device **states and bounds its own budget, in its own report, and is responsible for staying inside it**. No track is required to model a sibling's footprint, and no track inherits a neighbour's budget as a constraint on its own design. This withdraws the hand-off in 0160's risk 6 ("the envelope figure the fleet ships must be chosen against 0150's footprint too, and this belongs in whichever track ships second"), which named no owner and would have made the second track's design hostage to the first's unfinished report. Consequences run in both directions. **0160 already complies**: its envelope is a charter ruling (D-0040, 10–50 MB), worked at 20 MiB per tab and validated statically at construction by invariant I3, so its risk 6 is re-dispositioned rather than deleted. **0150 acquires an obligation its plan does not carry**: the plan states no footprint anywhere, and reserves "one eviction, quota, multi-tab, and worker decision" for its origin's IndexedDB without reserving a memory budget among them — on a RAM-disk device IndexedDB *is* RAM, so the store's footprint is a number that track's report owes rather than a browser concern it can defer to quota. **What this rule deliberately does not do is own the sum.** Per-track budgets compose only by addition and no artifact performs the addition; the OS on a RAM-disk device sees the total. At today's numbers the arithmetic is comfortable — 0160 contributes ~40 MiB of serialized bytes per device, nearer 80 MiB of heap by its own UTF-16 caveat, against the 6–16 GB of contended RAM intake item f reports, which is under 2% — so the residual is **recorded rather than mitigated**, with two reopening triggers: any single track's budget growing by an order of magnitude, or a third memory-holding component appearing. At either point a device-level ceiling to apportion becomes worth the coordination it costs.
**Why**: User ruling 2026-08-23, and it is the cheaper of the two available rules. The alternative — a device-level ceiling apportioned across tracks — needs a number nobody has (the RAM disk's headroom net of the OS and the other services item f describes as contended), a coordinator to divide it, and a re-division every time a track's needs change; it would also make each track's design contingent on a sibling's unfinished report, which is exactly the coupling the withdrawn hand-off created. Per-track ownership matches how this program already assigns seams, keeps each budget falsifiable inside the track that can actually measure it, and converts the cross-track hazard from an unowned analysis gap into an addition anyone can perform once both numbers exist. The cost is stated rather than hidden: nothing in this repo checks that sum, and this entry is the only place that says so.
**From**: user ruling 2026-08-23; tracks/0160-flight-recorder/report.md risk 6
**Affects**: 0160 (risk 6 re-dispositioned; envelope and recommendation unchanged), 0150 (its report must state and bound the store's footprint), and every future track that holds device memory
